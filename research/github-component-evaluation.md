# GitHub component evaluation

Reviewed 2026-11-20 against this repository's Next.js 16, React 19.2, Payload 3.94 and Node 24 stack. Research only: no installation, source-code change, external account or deployment. Versions below are versions observed in official source manifests, not a guarantee of the npm latest tag. Pin and verify the actual chosen release before adoption; main-branch docs and releases may differ.

## Existing dependencies first

`package.json` has no direct calendar, command-menu, table or chart library. `package-lock.json` already resolves `@date-fns/tz` 1.2.0 and `date-fns` 4.1.0 through Payload. The first is MIT in both the lock and upstream license. The current analytics chart is an original SVG implementation with pointer and keyboard handling. Payload already supplies collection listing, filtering, access control and its own date fields; a new generic grid should not replace those automatically.

## Strongest concrete incorporation

Use `@date-fns/tz` explicitly for the internal calendar's date model, not just text formatting. Construct the start of the viewed month and the start of the next month in Orlando, then convert those instants to ISO strings for the API range. Use the same zone to initialize Today and derive the selected month. Keep a clear split between day keys and UTC instants. Verify winter/summer offsets, the March/November DST boundaries, month rollover, and a browser outside Orlando.

The upstream docs show `TZDate` constructors with the IANA zone as the final argument. Validate the installed 1.2.0 API directly before using newer docs or helpers. No need to upgrade Payload or adopt a complete calendar application to solve this issue. An explicit dependency declaration prevents relying accidentally on hoisting.

Native labelled selects, buttons, search inputs and a live result-count announcement remain a sensible solution for doctor/status filters. A dependency should earn its cost through behavior the current controls cannot reliably provide.

## Complete applications considered and excluded

- [Chatwoot](https://github.com/chatwoot/chatwoot): its [root license](https://github.com/chatwoot/chatwoot/blob/develop/LICENSE) explicitly excludes `enterprise/`, whose [separate license](https://github.com/chatwoot/chatwoot/blob/develop/enterprise/LICENSE) restricts production use. The [Gemfile](https://github.com/chatwoot/chatwoot/blob/develop/Gemfile) establishes a separate Ruby/Rails application with database and Redis dependencies. Its inbox patterns may inform original UX, but installing it creates a new operational system and does not automatically activate SMS channels.
- The old [Cal.com GitHub path](https://github.com/calcom/cal.com) currently serves a [README](https://github.com/calcom/cal.com/blob/main/README.md) identifying **Cal.diy**, a separate self-hosted community edition. Its [license](https://github.com/calcom/cal.com/blob/main/LICENSE) is currently MIT; do not repeat an outdated blanket AGPL claim. The README says enterprise features were removed and recommends personal, non-production use. This is not an appropriate drop-in clinical scheduling upgrade. Commercial Cal.com and community Cal.diy must be evaluated as different products.

## Validation boundary

License files and manifests were read from official repositories. Compatibility above means declared runtime/peer ranges, not a successful integration build. None of these packages establishes clinical privacy compliance, provider connectivity, patient confirmations or financial attribution. Preserve upstream notices when distributing adopted code. Root implementation must still run focused type/build/browser checks for whatever is actually incorporated.
